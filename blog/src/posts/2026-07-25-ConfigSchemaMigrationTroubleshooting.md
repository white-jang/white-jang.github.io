### 서론

고교별조회는 사용자가 설정값에 따라 사이트를 커스터마이징할 수 있는 서비스이다. 제공되는 사이트에서 조회할 수 있는 데이터는 특정 고등학교의 지원자 데이터다. 진행했던 작업은 이 설정값에 새로운 옵션을 추가하는 기능 개발이었다. 예를 들어 오픈 시간 설정, 그리고 합격 상태 등 새로운 데이터 필드를 추가하는 작업이었다.

이 과정에서 설정값을 담고 있는 JSON 구조 자체를 변경해야 했다. 단순히 필드를 추가하는 일이라 크게 어렵지 않을 거라 생각했는데, 자체 QA 중 예상치 못한 곳에서 문제가 발생했다. 이미 서비스 중인 곳들에는 새로운 설정값이 전혀 반영되지 않는 현상이었다.

이번 글에서는 이 문제를 어떻게 발견했고, 왜 발생했는지, 그리고 어떻게 해결했는지 정리해본다.

### 문제 상황

새로운 설정 옵션을 추가하기 위해 고교별조회에서 사용하는 설정 JSON의 스키마를 변경했다. 처음 작업을 진행할 때는 고교별조회를 새로 생성한 서비스에서만 테스트를 했고, 이 케이스에서는 새 설정값이 문제없이 들어갔다.

문제는 이미 configData를 갖고 있던, 즉 기존에 운영 중이던 서비스에서 테스트를 시도하면서 드러났다. 이 케이스에서는 새로 추가된 필드가 아예 존재하지 않는 상태였다. 그제서야 "신규 생성"과 "기존 운영 중"은 서로 다른 케이스이고, 후자에 대한 검증이 빠져있었다는 걸 인지했다. 영향 범위를 확인해보니 운영 중인 서비스 중 약 40개 이상이 해당됐다.

다행히 이 문제는 실 배포 전, 매니저와 함께 자체 QA를 진행하던 중에 발견했다. 배포 후 장애로 이어지기 전에 잡을 수 있었던 케이스다.

원인을 파악해보니 생각보다 단순한 지점에서 놓친 부분이 있었다.

### 원인 분석

기존 서비스들은 이미 자체적으로 예전 버전의 설정 JSON을 DB에 갖고 있는 상태였다. 처음 작업할 때는 "새 스키마로 값을 내려주면 알아서 갱신되겠지"라고 단순하게 생각했는데, 실제로는 다음과 같았다.

- 신규 배포된 코드는 **새로운 기본 JSON 구조**를 기준으로 동작하도록 짜여 있었고
- 기존 서비스는 **예전 버전 JSON을 그대로 유지한 채** 서버에서 내려받고 있었기 때문에
- 두 값이 병합되지 않고, 예전 값이 그대로 사용되면서 새로 추가된 필드 자체가 존재하지 않는 상태가 됐다

즉, 새 설정값을 추가하는 배포였지만 **기존 데이터를 덮어쓰거나 마이그레이션하는 과정이 빠져 있었던 것**이 문제의 핵심이었다. 스키마만 바꾸고 기존 데이터와의 하위 호환성은 전혀 고려하지 못한 채 작업한 것이었다.

### 첫 시도의 한계

처음에는 단순히 새 필드를 포함한 JSON을 새로 정의하면 될 거라 생각했다. 하지만 이 방식은 다음과 같은 문제를 안고 있었다.

1. 이미 저장되어 있는 예전 버전 JSON을 무시하거나 강제로 덮어쓸 수 없는 구조 (기존 값 유지가 필요한 경우도 있었기 때문)
2. 서비스 수가 많아 일괄 마이그레이션 스크립트를 돌리기에는 리스크가 컸음

결국 클라이언트(Vue2) 단에서 로드 시점에 JSON 값을 체크하고 병합하는 방식이 더 안전하다고 판단했다

### 왜 서버/DB 마이그레이션이 아닌 클라이언트 정규화를 택했나

당시 작업 환경은 ASP.NET 백엔드 위에 Vue2가 올라간 구조였다. 근본적으로 해결하려면 서버 쪽에서 기존 데이터를 새 스키마로 일괄 마이그레이션하는 방법도 있었다. 이 경우 클라이언트는 이미 갱신된 데이터를 받기만 하면 되니 별도 정규화 로직이 필요 없다.

다만 이 방법은 백엔드(.aspx) 코드를 함께 수정해야 하고, 40개 이상 서비스의 실제 저장 데이터를 직접 변경하는 작업이라 잘못됐을 때 롤백 부담이 컸다. 고교별조회는 핵심 서비스가 아니었고, 그 안에서 기능 추가 수요가 있는 상황이었기 때문에 최대한 적은 비용으로 해결하는 쪽을 택했다. 백엔드는 건드리지 않고 프론트엔드 레이어에서만 처리하면, 리스크와 작업 범위를 크게 줄이면서도 문제를 해결할 수 있었다.

물론 이 방식은 예전 버전 데이터가 남아있는 한 클라이언트에서 매번 정규화 과정을 거쳐야 한다는 한계가 있다. 서비스의 중요도와 트래픽, 유지보수 비용을 고려했을 때는 이 정도 트레이드오프가 합리적이라고 판단했다.

### 해결 방법: 로드 시점에 버전 체크 후 병합

Vue 앱이 초기화될 때 서버에서 내려받은 설정값이 예전 버전 JSON인지 확인하고, 예전 버전이라면 새로운 필드를 spread 연산자로 병합해주는 방식으로 수정했다.

\* 아래의 코드들은 단순 예시로, 실제 서비스 코드와 무관하다.

```javascript
// 새로 추가된 필드를 포함한 기본(신규) 설정 객체
const DEFAULT_CONFIG = {
  schoolSearchOption: true,
  regionFilter: true,
  // v2에서 새로 추가된 필드 (예시)
  gradeLevelFilter: false,
  showRecentSearch: true,
};

function normalizeConfig(rawConfig) {
  if (!rawConfig) return { ...DEFAULT_CONFIG };

  // 예전 버전 JSON 여부 판단 (버전 필드 or 신규 필드 존재 여부로 체크)
  const isOldVersion = rawConfig.version === undefined || rawConfig.version < 2;

  if (isOldVersion) {
    // 기존 값은 유지하되, 새로 추가된 필드는 기본값으로 채워줌
    return {
      ...DEFAULT_CONFIG,
      ...rawConfig,
    };
  }

  return rawConfig;
}
```

```javascript
// Vue 컴포넌트 or 스토어 초기화 시점
async function initSchoolSearchConfig() {
  const rawConfig = await fetchConfigFromServer();
  const config = normalizeConfig(rawConfig);

  this.config = config; // 이후 앱 전역에서 안전하게 사용
}
```

포인트는 두 가지다.

1. **기존 값은 최대한 보존**한다 (`...DEFAULT_CONFIG, ...rawConfig` 순서로 스프레드해서 기존 값이 기본값을 덮어쓰도록)
2. 신규 필드만 기본값으로 안전하게 채워 넣어 **런타임에서 undefined로 인한 에러를 방지**한다

이렇게 하니 서버/DB 데이터를 직접 마이그레이션하지 않고도, 클라이언트 로드 시점에 자연스럽게 새로운 스키마로 정규화되는 효과를 얻을 수 있었다.

### 사후 검증

수정 후 곧바로 배포하지 않고, QA를 몇 차례 더 진행해 예전 버전 JSON을 가진 서비스와 신규 서비스 양쪽 모두에서 설정값이 정상적으로 반영되는지 확인했다. 배포 이후에도 일정 기간 모니터링하면서 예상치 못한 케이스가 없는지 지켜봤다.

### 배운 점

- **스키마 변경은 "새 필드 추가"가 아니라 "버전 마이그레이션"으로 접근해야 한다.** 특히 이미 운영 중인 서비스가 있는 경우, 기존 데이터가 새 스키마를 알지 못한다는 전제를 항상 깔고 작업해야 한다.
- **하위 호환성 체크는 배포 전에 반드시 시나리오로 검증해야 한다.** "신규 생성 케이스"만 테스트하고 "기존 운영 중인 케이스"를 놓치면서 문제가 발생했다.
- **자체 QA 단계에서 이런 문제를 잡아낸 게 결과적으로 컸다.** 40개 이상의 서비스에 영향을 줄 수 있었던 문제였는데, 배포 전 매니저와 함께 진행한 테스트에서 발견해 실제 장애로 이어지지 않았다. 이후로는 스키마나 설정값을 변경하는 작업일수록 "신규 케이스"뿐 아니라 "기존 운영 데이터 케이스"를 별도 시나리오로 꼭 넣어 QA하려고 한다.
- **클라이언트 단 정규화(normalize) 로직은 서버/DB 마이그레이션이 부담스러운 상황에서 유효한 임시 방편이 될 수 있다.** 다만 장기적으로는 서버/DB 쪽에서도 데이터 정합성을 맞추는 마이그레이션 작업이 함께 병행되는 게 맞다고 생각한다.

다음에 비슷한 설정값 스키마 변경 작업을 할 때는, 처음부터 "이미 존재하는 데이터는 예전 버전일 수 있다"는 걸 기본 전제로 두고 설계하려고 한다!
