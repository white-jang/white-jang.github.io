### 서론

회사에서 클로드 코드와 함께 퍼블리싱 자동화를 도전했던 기록을 적어보았다.  
왜 클로드 코드였는지? 어떤 방법을 선택했는지? 여러가지 갈림길 중 지나온 길을 걸었던 이유를 정리하려고 한다.

### 도입 배경

**회사에서 Winform(C#) 프로그램을 ReactJS 기반 웹으로 마이그레이션하게 되었다.** 이렇게 말하면 에? 별거 아닌 것 같은데? 싶은데, **출시한 지 15 년은 된 레거시 프로그램을 웹으로 주니어들끼리 옮기는 게 정말 쉬운 일은 아니었다.**
그리고 가장 큰 문제는!! **레거시 프로그램이 정말 최악의 UX를 가지고 있었다는 것이다.** (욕하는 것이 절대 아니다. 왜 그렇게 되었는지도 충분히 이해하고 있고, 4 년 동안 가장 많이 사용했던 사용자가 나와 팀원들이었다...)
사용자는 직무 순환 문제로 늘 능숙하지 않았는데, 기능이 너무 많아 프로그램이 복잡했고 그로 인한 사용자 문의를 전부 개발자가 떠안게 되는 굴레의 연속이었다.
따라서 기술 부채와 사용자의 러닝커브를 해결하고자 기획부터 디자인, 개발을 전부 해당 프로그램에 가장 익숙한 우리 팀이 하게 되었다.

### 조용한 암살자는 퍼블리싱이었다

기존 웹 서비스에 추가하여 서비스하자는 결론이 내려진 뒤, 마이그레이션 작업을 진행하기 시작할 무렵 진짜 문제를 깨달았다.
**팀원들 중 1 만자 이상의 기존 CSS 파일과 충돌되지 않도록 처리할 수 있는 인원이 나밖에 없다는 사실...... 즉, 퍼블리싱이 가능한 사람은 나 혼자였다.**
기존 CSS를 만들었던 퍼블리셔들은 어딘가로 모두 사라진 상태였다. (퇴사나 부서 이동 등...)
메인 업무가 있는 상황에서, Figma를 보고 **"내가" 퍼블리싱한 페이지를 완성해야 팀원들이 ReactJS 컴포넌트로 옮겨 기능을 붙이는 작업이 반복됐다.**
당시에는 AI와 함께 코딩할 수 있는 환경이 아니었기 때문에 내가 2~3일이 걸려 페이지를 완성하면 (이것도 메인 업무가 많지 않아 빠르게 만들었을 때 기준) 팀원들이 그제서야 작업을 시작할 수 있었기 때문에 개인적인 부담감도 컸고, 내가 팀에서 가장 경력이 많았던지라 메인 업무도 적지 않아 병목이 자주 생겼었다.

### AI: 쟈동화 할 거 없냐 쟈동화 🥴

마이그레이션 프로젝트의 1차 완성이 코 앞일 무렵, AX 열풍이 불기 시작했다. 자연스럽게 병목이 되던 퍼블리싱 문제가 주목 받았다. 퍼블리싱의 부재는 우리 팀만의 문제가 아닌, 개발부 전체의 문제였던 지 오래였기 때문이었다.
**그래서, 이 작업을 AI와 함께 해결해 보려했으나 어떤 방법이 가장 좋은지 해답을 줄 수 있는 사람이 없었다.
결국 직접 해 보고 비교할 수밖에 없었다.** 이 말은 AI가 발전하기 전에도, 지금도 항상 통하는 진리인 것 같다.  
어디로 가야 할지 모르겠다면? 일단 걸어 보자! 어떤 길이 짧은지는 걸어보지 않은 사람은 모르는 법이다.
이때 고민이던 것을 정리하면 이렇다.

- **Antigravity와 Claude Code 중 어떤 게 더 이 작업에 적합할까?**
- **Figma MCP를 활용하는 방식과 Image를 던지는 방식 중 어떤 게 더 좋은 결과물을 만들어 낼까?**

### 잠시만! 기준부터 세우자

**여기에서 중요한 점이 또 있다. "작업에 적합하다"와 "좋은 결과물"의 기준은 무엇인가?**
점점 AI가 발달하게 되면서 개발자의 작업 방식에 정말 큰 변화가 일어났다고 생각한다. 이것을 깨달은 사람과 아닌 사람의 차이도 클 것이라고 많은 아티클에서 얘기하고 있고, 나 또한 그렇게 생각한다. if 문 다음에 어떤 코드가 나올지만큼 이런 **추상적인 결과에 대한 정확한 정의가 중요해졌다고 생각한다.** 정확한 목표를 개발자가 알고 있어야 AI를 그 방향대로 움직일 수 있기 때문이다.
내가 생각했던 기준은 이렇다.

- 작업에 적합한 것이란?
  - 원하는 결과물을 얻기 위한 소통 비용이 적을 것
- 좋은 결과물이란?
  - CSS 품질이 좋은 것 - Class Naming, Selctor, 우선순위 등을 고려
  - 레거시 CSS와 톤을 동일하게 작성해줄 것
  - 파편화된 레거시 CSS와 충돌하지 않을 것

### Antigravity + Image를 시도했다! 그러나...

사내 프로젝트여서 이미지를 첨부할 수 없어 조금 아쉽다. 이미지를 설명하자면, 헤더와 사이드바가 있고 테이블이 3 개 존재하는 페이지의 캡처본이었다. 두 AI의 성능을 비교해 보고 싶어 일부러 가장 복잡한 페이지를 골랐다.
Antigravity로 이미지를 전달했을 때에는 여러 번 이미지를 분석하라고 하고, 정확히 어떤 div가 잘못되었는지 지적하니 얼추 비슷한 결과물이 나왔다.
하지만, 워낙 복잡한 생김새라 그런지 레이아웃 자체가 다른 부분이 있었고 한글 데이터의 인식률이 낮아 이상하게 추가해놓은 텍스트가 있었다. (eg. 개별 통화 → 계통 통화)
이 때 CSS 품질은 나쁘지 않았지만, 지나치게 포괄적으로 Class 이름을 지었기 때문에 기존 CSS와 충돌하지 않도록 추가로 처리해야 한다는 것을 깨달았다.
여기까지 시도해 보았을 때, **이미지는 원하는 수준까지 끌어올리려면 소통 비용이 너무 많이 들 것 같아 Figma MCP로 방향을 틀었다.**

### Antigravity + Figma MCP에서 새로운 문제를 만났다 🙀

Figma MCP를 연결하고 구현을 시도하다가 Figma 내의 구조에 이슈가 있다는 것을 깨달았다. 디자이너 없이 개발자들이 기획과 디자인을 진행했다 보니, **Figma 내에서 구조가 Group으로만 잡혀있어 HTML 레이아웃을 제대로 인식하지 못하는 문제가 있었던 것이다.**  
동일한 페이지를 Auto Layout했을 때, Group했을 때 코드를 비교해 보았더니 Auto Layout은 Element들 간의 위치 관계를 파악하여 div밑에 span 등 상위, 하위 구조로 HTML의 기본 구조를 잘 따랐다. 따라서 CSS 퀄리티도 전혀 문제가 없었다.
그러나, Figma 상에서 Group만 했을 경우 Element들 간의 관계를 파악하지 못해 전부 별개의 Element로 구현하여 CSS도 상하 관계를 이용하지 못하고 전부 `display: absolute;`로 처리하는 아찔한 결과를 얻었다.
이 실험을 표로 정리하면 이렇다.
| 항목 | Auto Layout | Group |
|---|---|---|
| HTML 구조 인식 | Element 간 위치 관계 파악 ○ | Element 간 관계 파악 불가 ✕ |
| HTML 출력 | `div` 하위에 `span` 등 상하 계층 구조로 생성 | 모든 Element를 별개의 독립 요소로 생성 |
| CSS 포지셔닝 | 상하 관계를 이용한 자연스러운 레이아웃 | 모든 요소에 `position: absolute` 적용 |
| CSS 퀄리티 | 문제 없음 | 유지보수 불가 수준 |
| MCP 코드 생성 적합성 | 적합 | 부적합 |

그럼 꼭 레이아웃을 Figma 상에서 잡고 가야 할까? 당시에는 이것 때문에 고민이 컸지만 지금 와서 생각해 보면 꼭 그렇지만은 않았다. 다른 방법으로 충분히 우회할 수 있는 수준의 이슈였다.
이후에 이 문제는 Figma는 전혀 수정하지 않고 Group을 유지한 채 Cluade Code를 사용하면서 기존 퍼블리싱 결과물을 학습시키고, md로 디자인 규칙 등을 세세히 잡아 해결했다. 이것은 나중에 새로운 글로 더 상세히 적도록 하겠다.

### Cluade: 이리 와... 많이 힘들었지? 🥹

지금까지 Antigravity로 진행했던 모든 작업을 Claude Code로 동일하게 시도해보았다. 현재는 Gemini도 업데이트를 진행하여 두 모델의 성능 비교가 어떨지 모르겠으나, 개발을 진행했던 당시(3월 초~5월 말)에는 Claude Code가 정말 압도적으로 우수하다고 느꼈다.
이미지를 주고 페이지를 생성해달라고 요청했더니, 이미지를 보자마자 Claude가 이미 Antigravity가 만들어놓은 결과물과 유사한 페이지인 것을 알아차리고 기존 결과물을 수정할 것인지, 새로운 HTML/CSS 파일을 만들 것인지 되물었다. 여기에서 정말 진한 감동을 느꼈다. Antigravity를 사용할 때처럼 마이크로 매니징 때문에 화가 날 일은 없겠구나!
**새로운 HTML/CSS 파일로 작업할 것을 지시하자 레거시 CSS를 분석하여 헤더, 사이드바, 푸터를 자동으로 적용하여 캡처 한 장만으로 Antigravity보다 퀄리티 높은 결과물이 만들어졌다.**
이후에 시도한 Figma MCP도 Group만 사용했음에도 완성도가 꽤 높은 결과물이 나왔다. Antigravity와 다르게 Figma MCP로 구조를 잘 읽어와 아이콘 이미지도 png 형태로 추출하여 버튼에 적용하는 모습을 보여주었다.
Claude가 만들어준 결과물이 훨씬 만족스러웠다. 그러나, 아직 한 번의 시도만으로 완벽하게 UI를 구현하지는 못했다. Figma 상에서 디자인 시스템이 정의되지 않았기 때문에 여전히 아쉬운 점이 조금 남아있었다.
그래서 이 뒤로는 계속 "디자인 고도화"라는 숙제를 풀기 위해 노력하기 시작했다.

### 디자인 고도화...... 너냐? 8반 이쁜이가?

"AI를 가장 잘 아는 것은 AI다." 라는 지론에 따라 Claude와 함께 `DESGIN_RULES.md` 파일에 구체적인 디자인 스펙을 작성했다. 기존의 퍼블리싱 결과물과 Figma MCP를 통해 디자인 특징을 추출하여 폰트 크기, 버튼 레이아웃, 강조 색상 등 디자인 시스템에서 정의할만한 내용들로 구성하고, `WORKFLOW.md`에 써있는 규칙에 따라 퍼블리싱 작업 시에 가장 먼저 참고하도록 해두었다.
그 다음, `PUB_RULES.md`에 기존 레거시 CSS에서 어떤 상황에서 클래스를 재사용할 수 있는지를 작성하고 참고하도록 했다.
어느 정도 퍼블리싱 결과물이 고도화됐다고 판단하고, 이후에는 완성된 HTML/CSS를 React Component로 옮기는 작업과 Figma에서 특정 코멘트를 달면 변경된 디자인을 반영하는 작업을 했다. 이 내용은 나중에 새로운 글로 더 자세히 적겠다.

### 회고

처음 업무에 AI를 적극적으로 도입해보았던 거라 AI 의존적으로 코딩을 함께 한다는 것이 상당히 어색했다. **이때 처음으로 "내가 어디까지 관여해야 할까?", "AI가 만든 코드를 얼마나 깊게 검증해야 할까?", "어떻게 해야 더 내 말을 잘 알아듣게 할 수 있을까?" 같은 고민을 하기 시작했고 정말 개발 패러다임이 바뀌었다는 게 실감났다.**
정말 운 좋게도 팀에 AI가 너무나도 필요한 상황이었고 그 덕분에 여러가지 시도해볼 수 있어서 좋은 기회였다. 이 작업을 맡기 전까지 AI 의존 코딩에 그다지 관심이 없었으나, 어느새 익숙해져 이제는 클로드 없이 개발할 수 없는 몸이 되어버렸다... _(책임져!! Anthropic: 오잉? 제가요?)_
그러나 아직도 여전히 AI를 어떻게 써야 잘 쓰는 사람이 되는 건지를 모르겠다. 계속해서 풀어나가야 하는 새로운 숙제인 것 같다.
